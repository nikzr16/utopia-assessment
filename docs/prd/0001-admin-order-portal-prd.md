## Purpose

Admins at Sejuk Sejuk Service take customer requests by phone and walk-in and
need to turn each one into a service order, assign a technician, and tell that
technician about the job. Today the foundation (0000) can store and move
orders, but there is no screen for it. This PRD defines the Admin portal:
creating orders, finding them again, keeping them correct, and dispatching
technicians.

Source: Module 1 of `docs/prd/0000-programmer-assessment-brief.docx`.

## Goals

- An Admin can create a complete, valid service order in under a minute on a
  desktop, with every field the brief lists.
- The order number is generated by the system and shown back to the Admin as
  soon as the order is saved, with a summary of what was saved.
- The Admin can tell the assigned technician about the job through WhatsApp
  with one tap, with the job details already filled in.
- The Admin can find any order again, see its current state and history, fix
  its details, and assign, reassign, or cancel it.
- Bad input (invalid phone numbers, impossible prices, missing fields) is
  caught with a clear message before anything is saved, and the database
  rejects it even if a screen misses it.

## Non-Goals

- Technician, Manager, and Finance screens (0002 onward). Their role homes
  stay as they are.
- Automatic WhatsApp sending through the WhatsApp Business Cloud API. The
  WhatsApp part is a `wa.me` deep link the Admin taps to send (decided in 0000).
- The customer-facing WhatsApp message on Job Done (0003).
- A customer list or customer lookup for repeat customers (0000 plan: customer
  details are stored per order).
- Branch-based access restrictions (0000 plan: non-technician staff see all
  branches).
- Bulk actions, CSV import/export, and printing.

## Scope

| In Scope | Out of Scope |
|---|---|
| New order form with every brief field, writing through `create_order` | Technician job screens (0002) |
| Order summary after submission | Customer WhatsApp message on Job Done (0003) |
| WhatsApp deep link (`wa.me`) to notify the assigned technician | WhatsApp Business Cloud API |
| Admin order list with search and filters | KPI dashboard (0004) |
| Order detail with current state and history | Customer records / lookup |
| Editing an order's details (new database function, audited) | Changing completion, payment, or review data |
| Assign, reassign, and cancel from the screen through `transition_order` | Bulk actions, import/export |
| Validation of Malaysian phone numbers and quoted price, in the screen and in the database | Branch-based data restrictions |
| Responsive layout: desktop first, usable on tablet and phone | Offline use |

## User Stories

1. **As an Admin**, I want to fill in one form with the customer, the problem, the service type, the price, and the technician so that the job is captured in one go.
2. **As an Admin**, I want the order number to be created for me so that numbers are never duplicated or mistyped.
3. **As an Admin**, I want to see a summary of the order right after I save it so that I can read it back to the customer and catch mistakes.
4. **As an Admin**, I want to send the job to the technician on WhatsApp with one tap so that they know about it straight away without me retyping the details.
5. **As an Admin**, I want to save an order without a technician and assign one later so that intake is never blocked by scheduling.
6. **As an Admin**, I want to search orders by order number, customer name, or phone so that I can answer a customer who calls back.
7. **As an Admin**, I want to filter orders by status, branch, and technician so that I can see what still needs dispatching.
8. **As an Admin**, I want to correct an order's details so that a typo in an address does not send a technician to the wrong place.
9. **As an Admin**, I want to reassign or cancel an order from its page so that I can react when a technician is unavailable or a customer cancels.
10. **As an Admin**, I want to see who changed an order and when so that I can explain what happened to it.
11. **As an Admin**, I want to be told exactly what is wrong with a phone number or price so that I can fix it before saving.

## Product Decisions

Decisions already fixed by the brief or by 0000:

| Decision | Rationale |
|---|---|
| Every write goes through a database function; the actor is the signed-in Admin | 0000 rule: the database is the rule authority and nobody can act as someone else |
| Order numbers are `ORDER` + a sequence (`ORDER1001`, …), generated by the database on save | 0000 plan; matches the brief's samples |
| Saving with a technician creates the order as **Assigned**; without one, as **New** | 0000 `create_order` behavior |
| Customer details are stored on each order | 0000 plan; the brief's form captures them per order |
| WhatsApp is a `wa.me` link the Admin taps to send; the in-app notification to the technician is created by the database automatically | 0000 decision; `wa.me` cannot send by itself |
| Reassign is allowed only from Assigned or Acknowledged; cancel only from New, Assigned, or Acknowledged, with a reason | 0000 transition table |
| Which actions a screen offers comes from the `src/domain` transition mirror; the database still decides | 0000 rule: hiding a button is not the protection |
| Amounts are shown in MYR (`RM 1,234.50`); dates and times in Malaysia time (UTC+8) | 0000 cross-cutting rule |

Decisions made by this PRD (Open Questions answered 2026-10-22):

| Decision | Rationale |
|---|---|
| Admins get a real portal: order list as their home, new order form, order detail | The brief's form alone leaves no way to find, fix, or dispatch an order after saving |
| Editing order details is a new audited database function, not a direct table write | Keeps the "all writes through RPCs" rule; the audit log shows what changed |
| Phone and price rules are enforced in both the screen (instant feedback) and the database (cannot be bypassed) | Same pattern as the transition rules: one rule, two places, kept in step by tests |
| The form shows the order number as "Generated on save"; the summary shows the real number (Q1) | A previewed number can be wrong when two Admins save at once; reserving numbers leaves gaps |
| Branch is a dropdown that defaults to the Admin's own branch (Q2) | Admins take orders for every branch, but most are for their own |
| Technician dropdown lists all active technicians, the order's branch first, each with their open-job count (Q3) | Lets the Admin dispatch across branches and spot who is free |
| Phone numbers: Malaysian mobile and landline in any common format, stored as digits with country code (`60123456789`), shown formatted (Q4) | One stored form makes search and `wa.me` links reliable; landline customers are not blocked |
| Quoted price: RM 0.00 to RM 100,000.00, at most 2 decimals; zero allowed (Q5) | Zero covers warranty and free follow-ups; the cap catches typing slips |
| Details are editable while New, Assigned, or Acknowledged; the technician changes only through assign / reassign (Q6) | Once work starts the price belongs to the technician's completion record |
| An edit that changes job details notifies the assigned technician in-app, and the WhatsApp button is offered again (Q7) | The technician must not work from stale details |
| The WhatsApp message carries the full job details (Q8) | The technician can act without opening the app |
| Optional scheduled date and time on the form and in editing (Q9) | `create_order` already supports it; reschedule and the dashboard use it |
| Reschedule / postpone with a reason is available on the order detail (Q10) | `reschedule_order` already allows Admins; keeps the reschedule log complete |
| Order list: all branches, newest first, 25 per page; search by order number, customer name, or phone; filters for status, branch, technician, and scheduled date range (Q11) | Matches 0000's all-branch visibility; search covers the "customer calls back" case |

## Constraints

- Writes only through RPCs: `create_order`, `transition_order`, and any new
  function this feature adds. No direct table writes from the browser.
- 0000 migrations are committed: any database change is a new timestamped
  migration (append-only). A rule mirrored in `src/domain/` must stay in step
  with the database, checked by a test.
- Real authentication stays: only a signed-in Admin with an active staff
  profile can use the portal; other roles never see it, and the database
  rejects their writes anyway.
- Brief stack: React, Tailwind CSS, Supabase. No new paid services.
- The hosted Supabase project already has 0000 applied; any schema change
  ships with SQL the user can run there.

## Open Questions

Each question lists options; **(Recommended)** marks the proposed default.
All answered 2026-10-22: option (a) for every question (see Product Decisions).

- [x] **Q1. Order number on the form.** The database creates the number on save.
  - (a) The form shows "Generated on save"; the summary shows the real number. **(Recommended)**
  - (b) Preview the next number on the form. It can be wrong if another Admin saves first.
  - (c) Reserve a number when the form opens. Abandoned forms leave gaps in the sequence.
- [x] **Q2. Branch of the order.** `create_order` needs a branch; the brief's form has none.
  - (a) Branch dropdown, defaulting to the Admin's own branch. **(Recommended)**
  - (b) Always the Admin's own branch; no choice on the form.
  - (c) Branch dropdown with no default; the Admin must choose.
- [x] **Q3. Technician dropdown.**
  - (a) All active technicians, the order's branch first, each with their count of open jobs. **(Recommended)**
  - (b) Only technicians of the order's branch.
  - (c) All active technicians in one alphabetical list.
- [x] **Q4. Phone number rules.**
  - (a) Accept Malaysian mobile and landline numbers in any common format (`012-345 6789`, `+60 12 345 6789`, `03-1234 5678`); store them normalised as digits with country code (`60123456789`); show them formatted. Enforced in the screen and the database. **(Recommended)**
  - (b) Mobile numbers only (`01x`). Blocks customers who give a landline.
  - (c) Validate in the screen only; store as typed. The database would accept bad numbers.
- [x] **Q5. Quoted price rules.**
  - (a) RM 0.00 to RM 100,000.00, at most 2 decimals; zero allowed (warranty or free follow-up jobs). **(Recommended)**
  - (b) Must be more than zero.
  - (c) No upper limit beyond what the database column holds.
- [x] **Q6. Editing an order.**
  - (a) Customer details, problem, service type, quoted price, scheduled date, admin notes, and branch are editable while the order is New, Assigned, or Acknowledged; the technician changes only through assign / reassign. **(Recommended)**
  - (b) As (a), but also while In Progress. The price could change under a technician already on site.
  - (c) No editing; cancel and create a new order.
- [x] **Q7. Tell the technician about an edit.**
  - (a) Create an in-app notification for the assigned technician when an edit changes job details, and offer the WhatsApp button again. **(Recommended)**
  - (b) No notification; the Admin calls or messages the technician themselves.
- [x] **Q8. WhatsApp message content.**
  - (a) Full job details: order number, service type, customer name and phone, address, problem, scheduled date, quoted price, admin notes. **(Recommended)** The technician can act without opening the app.
  - (b) Short message: order number, service type, area, and "open the app for details". Keeps customer details inside the app.
- [x] **Q9. Scheduled date on the form.** The brief's form has none, but `create_order` supports it and later modules use it.
  - (a) Optional date and time field on the form and in editing. **(Recommended)**
  - (b) Leave it out of 0001.
- [x] **Q10. Reschedule from the Admin portal.** `reschedule_order` already exists and allows Admins.
  - (a) Include reschedule / postpone with reason on the order detail. **(Recommended)**
  - (b) Leave it out of 0001; the scheduled date is set through editing only.
- [x] **Q11. Order list defaults.**
  - (a) All branches, newest first, 25 per page; search by order number, customer name, or phone; filters for status, branch, technician, and scheduled date range. **(Recommended)**
  - (b) As (a), but default to the Admin's own branch.
  - (c) Open orders only by default (hide Closed and Cancelled).
